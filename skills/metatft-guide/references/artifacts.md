# 神器：从棋子到定阵候选

用户要的是拿到神器后可以玩什么，不是泛泛列神器名称。更新三个关联视图：
- 神器 → 具体携带者 → 阵容候选树。
- 棋子 → 可考虑的神器 → 各阵容的证据。
- 每套阵容详情中的神器分配、触发条件和使用样本。

## 证据提取

先核对赛季词库中 `items[].tags` 的 `Item.Equippable.Item.Artifact`，不要把光明装备、普通成装或纹章混入。必要时检查本版本的新标签，不沿用旧版32件数量。

历史详情中的 `results.itemNames[]`：`itemNames` 是物品API标识，`units[]` 记录棋子、count、avg、place_change。通过中文词库 `units[].apiName` 与 `assetNames[]` 映射棋子名。只把同一阵容中该棋子的记录称作该阵容的证据；不存在 `units` 时不要猜携带者。

用 `scripts/build_artifact_index.py SOURCE_DIR OUTPUT_DIR` 构建完整记录、常见候选和反向索引。默认保留所有来源返回的携带者和记录，包括主模板之外的变体与低样本。`--min-count` 仅用于低样本标签，不删除行。不固定每人前4项，也不将使用记录当成强度推荐。

## 解释与筛选

- 读当前版本神器机制；必要时核对英雄技能。机制解释不能仅凭物理/法系标签。
- 重点检查施法后普攻、持续攻击、眩晕、护盾、邻格站位、延迟触发、攻速锁定、死亡触发等条件。
- 样本量/平均名次是观察记录，未控制星级、其他装备、阶段、经济及幸存偏差。不能说使用次数多就最优，不能把负名次差当因果提升。
- 出装记录本身只能支持“可能候选”。若列为优先推荐，还需机制判断或对应高手攻略证据。纯机制推断没有记录时单独标明。
- 小样本条件阵容不强行扩充推荐；目录可保留“未有充分候选”。
- 神器占用装备格，不是第四件装备；保留必要转职、续航和生存配置。名单匹配不等于可以立刻卖掉打工单位。

## 页面与交付

按神器、棋子或阵容搜索；每个候选显示携带者、样本量、适用限制和来源链接。所有静态目录可直接阅读，动态筛选不应导致空白页面。链接到被筛选隐藏的神器时先恢复目标可见。

如果以后把神器接入多条件摇摆地图：神器 → 携带者 → 阵容的集合再与海克斯和开局集合交叉，保留携带者条件；同一个神器能被某个挂件使用，不自动代表有足够理由转整套阵容。

网页内容补充与技能更新是不同操作。用户要求同步技能时，更新技能说明、相关脚本、历史样例与分享ZIP；不要只改当前网页后声称技能已更新。
